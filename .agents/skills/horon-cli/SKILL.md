# Horon 使用说明书

Horon 的开发目的是让 AI 拥有长期记忆，并能依靠积累的知识自主规划、行动和调整方向。知识可以存入概念节点，通过 Tag 组织和检索；事件可以触发通知或相关记忆的阅读推荐；长期计划可以写成拓扑图，通过电位变化推导依赖、分支和全局状态。

## 调用入口

在仓库根目录运行：

```bash
python frontend/cli.py <命令> [参数]
```

Horon 数据的读取与修改统一通过这个入口。大批量操作统一使用 `batch --file` 执行，**严禁编写脚本直接读写底层 SQLite**（会绕过保留概念保护、外键与向量同步）。后文省略入口的命令均接在此后；尖括号参数由实际内容替换。参数细节可用 `python frontend/cli.py <命令> --help` 查看。

### 会话开始时

- **每次新会话（包括上下文压缩之后）**，先运行 `python frontend/cli.py login [--recent N]`。无论在线还是离线都要运行，它依次输出：
  1. `[1/3] Horon 使用说明书`：当前说明书正文；
  2. `[2/3] 启动节点`：所有挂载系统保留 Tag `boot` 的概念全文（逐个 `read_concept` 展开并记录注意力转移；修改启动清单使用 `add/delete <节点> tag boot`）；
  3. `[3/3] 最近修改的节点`：最近变更过的 N 个节点摘要（默认 `N=10`，`0` 表示隐藏）。
- **在线与离线**：对话上下文中出现 Hook 注入的 Horon 启动广播，就是在线接入。这条广播在对话上下文里，不在 CLI 的终端输出里。在线时会感知对话与工具事件、送达通知、执行工具门禁。没有这条广播就是离线：仍可读写节点、构建电路、手动更新电位，只是没有事件感知和门禁。

# 1. 概念怎样承载记忆与状态

一个节点承担一个可复用的概念：它可以是组织相关知识的联想枢纽，也可以是参与电路的可操作状态。例如，一个项目节点可以汇集项目目的、相关知识、执行路线和成果入口；一个状态节点可以表达某项工作是否达到判定标准。

同一概念使用同一个规范节点，相关观察和经验汇入它的正文。别名用于容纳同一概念的不同称呼。没有独立检索、关联或状态作用的零散内容，放入相关概念正文。

## 名称、正文与书腰（disclosure）

以下要求适用于所有角色：

| 字段 | 作用与要求 |
| :--- | :--- |
| `name` | 概念的名称。起名的唯一标准：一个对本图谱一无所知的人，光看这串字符产生的期待，必须与正文实际内容的主体、形态和作用域完全吻合。 |
| `content` | 解释概念，保存属性、知识、观察与凭据。正文和相关依赖必须支撑名称引发的全部期待。 |
| `disclosure` | 概念的书腰。写明“在什么情况下需要打开此节点”，供 intent 语义搜索匹配与推荐。 |

### 起名自检（门把手盲盒测试与 Affordance 示能）

概念的名称是图谱唯一的检索与认知入口。**起名的本质是设计一把好用的“门把手”（Affordance / 示能）**：
- **好的门把手**（如平铁板提示“推”，拉手提示“拉”）：让一个毫无上下文的初访者，在外界发生特定任务情境时，能本能地抓对把手，并且推开后拿到的东西与把手预期完全吻合。
- **坏的名字（死于缺乏陌生读手的抓手感）**：
  - **抽象口号 / 悬空大词**（如 `系统优雅降级`、`验证不等于调通`）：没有操作落点与触发情境，读手不知道何时该碰它；
  - **自我定罪 / 情绪标签**（如 `我拿答案调参当验证的毛病`、`我遇到报错就发呆`）：写作者沉溺于内部事后情绪，丢失了外部触发场景与输出形态（现场读手急需的是 `Bug修复验收准则` 或 `API限流退避策略`，绝不会在危机现场去检索“谁在发呆”）；
  - **句子化臃肿**（如把前因后果堆成20字长句）：把门把手做成了一块写满说明书的沉重石碑；
  - **容器口号化**（如 Tag 叫 `重构不是重写`）：把主张观点当成容器，看不出里面装什么成员。

**根病**：以上所有坏例都源于**起名时站在写作者的事后总结视角，而不是读者的即时交互视角**。名字是写给一个面对全新现场、需要快速决策的读者看的，必须钉死**【触发场景 + 交互形态/状态】**。

#### 各角色命名结构与形态词法则（6–12字为佳）

| 角色 | 读手交互期待 | 命名结构 | 推荐形态词 | 好例 | 坏例（病因） |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **规范/知识** (`plain`) | 在特定场景下该怎么做、有什么依据 | `[场景/对象] + [形态词]` | `准则` / `指引` / `规范`（执行路径）<br>`策略` / `方案`（分支降级）<br>`清单` / `记录`（检查项与事实）<br>`……时的应对`（情境节点：当前判断＋原始记录） | `Bug修复验收准则`<br>`跨模块调用适配规范`<br>`API限流退避策略`<br>`对外发布脱敏规范` | `验证不等于调通`（口号悬空）<br>`我拿答案调参当验证的毛病`（自我定罪，无场景形态）<br>`通信脱敏`（领域大词，无场景也无形态）<br>`发布脱敏规范`（省字致歧义：像动作指令而非规则） |
| **事实/状态** (`sensor/logic`) | 某事已完成、具备可核验依据 | `[对象/动作] + [完成/通过/就绪]` | `已完成` / `已通过` / `就绪` | `正则脱敏扫描已通过` | `轻量脱敏脚本检查`（未说明是状态还是工具）<br>`已扫描`（对象悬空） |
| **门禁** (`guard`) | 拦截并放行某个具体高危操作 | `放行 + [操作/工具]` | `放行` | `放行horon-cli执行` | `放行CLI`（动作与对象悬空）<br>`工具门禁`（把类型当成了指令） |
| **集合/工程** (`Tag`) | 容器，一眼看清里面装什么成员 | `[范围/用途] + [清单/库/工程]` | `清单` / `库` / `工程` | `待重构历史模块清单` | `重构不是重写`（口号句，不知道装什么）<br>`模块`（范围无限大） |

### 读到名字不符，当场改

名字是当初的人按当初的理解取的，并不因为已经存在就正确。旧库迁入的一批尤其如此——那些名字多半是照着书腰反推出来的，没有通读正文，本质是猜的。

因此每次 `read_concept` 都是一次复检：读完正文回头看名字，主体、形态、作用域与正文对不上，立刻 `set <名称或ID> name <新名称>` 改掉，不要留给"以后统一整理"。名字是这条记忆唯一的检索入口，错名不是瑕疵，是让这条记忆此后再也打不中。改名不影响正文、别名、Tag 与电路绑定。

同时检查一个信号：如果不在名字里塞一个"与"就概括不了正文，那多半不是名字该写长，而是这个节点装了两件事，应当拆开，或者把结论移回正文、名字只留主体。

## 四种角色

| 角色 | 用途 | 电位 |
| :--- | :--- | :--- |
| `plain` | 知识、实体、项目说明等联想枢纽，默认角色 | 恒为 0，不参与电路求值 |
| `sensor` | 事件或事实输入，包括手动维护的小目标状态 | 0 或 1，由事件或手动操作更新 |
| `logic` | 组合条件、分支与时序 | 根据上游条件派生 |
| `guard` | 以电路条件控制工具调用 | 根据上游条件派生，通电表示放行 |

名称和正文决定节点表达什么，角色决定它是否以及怎样参与电路。知识的内容并不因 plain 的电位为 0 而失效；电位只用于电路状态。

# 2. 保存、组织和读取知识

## 正文写入

创建节点时，名称应当准确指向概念本身，正文记录具体事实与排查依据，`--disclosure` 则是节点的书腰，写明“在什么情况下需要打开它”，供 intent 检索匹配。必须提供非空正文（`--content` 或 `--content-file` 二选一）。

短正文直接传给 `--content`。长正文或包含多行换行、复杂引号的内容，可先写入 UTF-8 文件后直接使用 `--content-file <文件路径>` 传入创建，正文内部换行与字符会完整保留；后续若需追加材料或记录，使用 `--append` 或 `--append-file`。

## 更新正文

`--append` 追加材料，`--old/--new` 局部替换已有表述；长文本可使用对应的文件参数，保留文件中的换行。当前判断改变时替换旧表述，需要留存的观察过程可以追加。

```text
update <节点名或ID> content --append "新增观察"
update <节点名或ID> content --old "待修正的原文" --new "修正后的内容"
update <节点名或ID> content --old-file <原文片段文件> --new-file <替换片段文件>
update <节点名或ID> content --old "段落开头...段落结尾" --new "整段替换后的内容"
```

`--old` 可用 `...` 省略中间，替换从开头到结尾的整段；两端需逐字命中且结果唯一。旧文原样能命中时优先按原文处理。局部替换要求旧文唯一匹配；未命中或命中多处会报错，此时重新读取正文并扩大匹配上下文。追加与替换不能在同一命令中混用。

### 什么时候该动笔写记忆

口头说“记下了”而不调用工具，等于没有发生。写入分两种，不在同一时刻做：**记录**当场写，只写发生了什么；**自省**事后写（自主运行、心跳或复盘时）。被批评的当下写解释，容易写成认错稿或自我开脱。

#### 记录（当场写，先写再回复）

| 场景 | 写法 |
| :--- | :--- |
| 新实体、新状态、关键数据首次证实 | 在对应节点 `--append`；新实体用 `create_concept` |
| 已记录的事实被证明不对 | `--old/--new` 当场改掉（只限事实；情境节点的“当前判断”只在自省时改） |
| 用户的处境、约束、偏好有实质变化 | 更新对应的人物或协作节点 |
| 某个情境又出现了：做法被批评、预测落空、得到明确反馈，或你照着/偏离了当前判断行事 | 在对应情境节点 `--append` 一条原始记录，结果好坏都记，不写诊断 |

对话顺畅、话接得快的时候最容易忘记写，停一下检查。

#### 情境节点

同一情境下每次做了什么、得到什么，放在同一个节点里，偏向才看得出来。用 `intent` 找书腰描述该情境的节点；没有就按情境新建（如 `用户深夜说身体疼时的应对`），`--disclosure` 写这个情境的触发描述，否则下次找不回来。新建时当前判断可以先写“（尚未自省）”。

```text
## 当前判断        ← 自省时改写
理想、现状、做法、预期、失败判据（注明改写日期）

## 原始记录        ← 只追加
- [时间] 情境 ｜ 我做了什么 ｜ 结果（对方原话/工具原始结果）
```

#### 自省

读原始记录，看出同一情境下的偏向和它的原因，再改写当前判断。如果记录里永远是同一种做法，它们只能说明这一种做法的后果；下次换一种做法试。

## Tag

Tag 从主题、项目或用途等方向组织节点，也可以用于筛选目标、施加结构约束或挂载插件。同一节点可以属于多个 Tag；Tag 成员关系本身不形成电路依赖。

创建 Tag 通常有两种起点：

- **工作中归集已有节点**：已经有几个节点需要一起检索、检查或维护，因此建立 Tag。源节点说明归集用途、成员范围和已有入口。
- **先立项，再展开节点**：已经决定推进具体工作，先建立项目 Tag，再随工作展开创建并纳入成员。源节点说明立项原因、整体目标与完成标准、当前阶段和下一步。初期成员可以很少，但项目要做什么应当明确。

仅保存一条知识时，可以先保留知识节点；出现共同管理的需要或明确立项意图时，再创建 Tag。

每个普通 Tag 由同名源节点注册，名称必须匹配源节点的正式名称，不能使用别名。源节点自动成为首个成员。注册和纳入成员的操作关系为：

```text
create_concept <Tag名> --disclosure "在什么情况下需要打开这个集合" --content "这个集合的实际用途、范围与入口"
create_tag <Tag名>
add <已有节点名或ID> tag <Tag名>
```

源节点需要长正文时使用正文文件参数（`--content-file <文件路径>`）。若同名源节点已经存在，读取并按需更新后直接注册。成员可以先于 Tag 存在，也可以在立项后逐步创建。

源节点的正文承担解释整个 Tag 簇的责任。如果这个 Tag 代表一个具体的**工程项目**，同名源节点就是该项目的总览入口，正文必须交代清楚项目的整体目标、所处阶段以及核心入口；当往这个 Tag 挂载新成员节点时，也应在源节点正文中说明该成员在项目全局里承担什么职责、处于哪一步。Tag 命名规则见第一节"起名自检"。

## 检索与阅读

| 可用线索 | 命令 | 结果 |
| :--- | :--- | :--- |
| 名称、别名或 ID | `read_concept <节点名或ID>` | 节点正文、属性及关联信息 |
| 关键词 | `search_concepts <关键词>` | 名称、正文等内容中的匹配节点 |
| Tag | `list_concepts --tag "Tag 表达式"` | 包含指定 Tag 成员的节点清单（支持 AND/OR） |
| 场景、疑问或意图 | `intent "具体疑问或情境"` | 书腰（disclosure）与描述语义相关的节点 |
| 最近修改 | `recent [N]` | 从审计日志拉取最近修改过的 N 个节点（操作统计与书腰） |

检索结果用于定位节点，选中后通过 `read_concept` 读取正文与关联信息（支持传入节点名、别名或数字 ID）。关键词搜索可以用 `--tag` 限定范围。`intent` 也可用于主动探索尚不知道名称的知识；它依据书腰检索，不会自动建立事件检测器。`recent` 用于快速回溯近期或上一会话被增删改过的概念。

### 怎样自然地主动拉取记忆（何时读 vs 何时查）

记忆不会自动常驻脑内。在当前会话中，**只要你不主动调用 CLI 调取，过往经验对当下的你来说就等于彻底不存在**。不要凭“脑子里大概有印象”去盲猜事实。

读到的是过去某次的经验和判断，可能过时、片面或写错。它是这次判断的材料，判断仍由当下的你来做。

- **什么时候「读」（`read_concept` —— 已经看到门把手）**：
  - **把手来源**：上下文中出现过的**概念名称、ID 或书腰浮标**（来自 Boot 子清单、历史轮次读取概念时浮现的 `[ YOU MAY ALSO NEED ]` 推荐、或 Tag 成员列表）；
  - **触发时机**：
    1. **名字命中直觉**：概念名字本身（如 `API限流退避策略`、`跨模块调用适配规范`、`Salem发起黑色玩笑与调情时的应对`）与当前任务情境高度契合，哪怕尚未展开书腰；
    2. **书腰命中场景**：当前情境、用户输入或即将执行的动作，触发了浮标中的 `When: ...` 条件；
  - **操作**：不要猜、不要凭概率硬写，直接 `read_concept <ID或名称>` 调出正文。

- **什么时候「查」（`intent` / `search_concepts` —— 上下文完全没有把手）**：
  - **触发时机**：
    1. **未知输入**：用户提到了未展开的专有名词、项目代号、历史约定或个性化偏好；
    2. **关键动作前夕**：准备提出非通用方案、执行高危变更、调用工具修改配置前，需要核验是否有沉淀过的规范或情境记录；
    3. **收到纠偏信号**：用户指出“理解错了”、“不对”、“偏离了目标”，或是长上下文任务目标漂移需要定位修正记录时；
  - **操作**：有明确专有名词时用 `search_concepts <关键词>`；不确定确切名字时用大白话向 `intent "<当前情境或心里想确认的疑问>"` 描述场景，靠书腰语义打捞。

# 3. 把长期计划写成电路

电路表达目标之间的关系。你可以把一个长期方向细化为阶段和小目标，用共同前置表达依赖，用可选路线表达分支。执行和反馈改变输入电位后，下游状态随拓扑重新计算，从局部变化看见全局影响。

## 输入与凭据

sensor 的 `1` 表示定义的状态成立，`0` 表示尚未成立或已经失效。

节点的电位变化由其角色与生命周期通道驱动：
- **客观事实 (`permanent` sensor)**：跨会话保留并手动维护的事实，使用 `--lifespan permanent`。人工确认并保存依据后，通过 `set <事实状态名或ID> active 1` 维护，事实失效时设为 `0`；
- **运行时感知 (`turn` / `session` sensor)**：配置 `sensor_hook`，在系统捕获到匹配事件时由 Hook 自动点亮并随回合或会话重置；
- **逻辑与守卫 (`logic` / `guard`)**：电位完全由上游依赖条件自动推导派生。

```text
create_concept <事实状态名> --role sensor --lifespan permanent --content "该状态的判定标准与适用范围"
```

将 permanent 输入置为 1 前，正文必须已有可核实依据，例如成果版本与路径、检查命令及结果、验收记录。完成标准说明“怎样才算成立”，实际凭据说明“这一次为什么成立”。已有依据仍适用时无需重复追加。

实际完成并保存凭据后，更新电位并读取相关下游：

```text
update <事实状态名或ID> content --append-file <实际凭据文件>
set <事实状态名或ID> active 1
read_concept <依赖该事实的节点名或ID>
```

事实失效时，修正正文依据并用 `set <事实状态名或ID> active 0` 更新输入。更换成果版本后，需要重新判断旧凭据是否仍适用。

## AND、OR 与 CHAIN

logic 与 guard 使用 `activation-rule` 连接已经存在的输入节点。下表中的 A、B 代表真实节点名（亦可使用节点 ID），实际命名仍需符合第一节的要求。

激活规则只支持单种运算符连接两个或多个节点，不支持括号 `()` 或复合表达式：

| 规则 | 表达的关系 | 局部行为 |
| :--- | :--- | :--- |
| `A & B` | 两项共同前置 | A=1、B=0 时为 0；两项都为 1 时为 1 |
| `A \| B` | 两条替代路线 | A=1、B=0 时为 1；A 失效后，若 B=1 仍保持 1 |
| `A → B` | 输入事件依次发生 | 收到 A 后等待 B；顺序推进到终点时成立（使用 Unicode `→`，不接受 `->`） |

- **单前置简写**：logic 与 guard 都可以只绑一个前置（`--activation-rule "A"`），系统归一化为单输入 `AND`，即 A 通电且未被抑制即成立。
- **单前置要配抑制**：`A UNLESS B` 表达「A 发生了而 B 没发生」，是监督与报警条件的常用形状。若单前置不带任何抑制源，它只是把 A 的电位原样转发一遍，这种情况直接用 A 本身，不要建节点。

```text
create_concept <组合状态名> --role logic --activation-rule "A & B" --content "为什么需要这两个条件，以及它们共同成立表示什么"
```

若需表达多层或组合条件，通过分层定义中间 logic 节点来实现：例如要表达 `A 之后满足 B 与 C`，先创建组合节点 `M`（规则为 `"B & C"`），再建立顶层规则 `"A → M"`。

输入变化后，下游随拓扑自动重新求值。诊断链路时，顺着 `read_concept <目标名或ID>` 的 Circuit 题头向上回溯：若发现某个直接前置标记为 `[OFF]` 或被 `UNLESS` 抑制，继续 `read_concept <该前置>`，直到定位到底层未就绪的具体传感器与判定依据。新路线和依赖可以按实际认识调整。

## 读取 Circuit 题头

以下是彼此独立的局部状态示意：

```text
Circuit: AND( A [ON], B [OFF] ) = OFF
Circuit: OR( A [ON], B [OFF] ) = ON
Circuit: CHAIN( A [✓] → B [⏳] ) = OFF
```

| 符号 | 含义 |
| :--- | :--- |
| 输入旁的 `[ON]` / `[OFF]` | 对应输入当前电位为 1 / 0 |
| 末尾 `= ON` / `= OFF` | 当前 logic 节点的求值结果 |
| 末尾 `= PASS` / `= BLOCKED` | 当前 guard 通电放行 / 未通电阻止匹配调用 |
| CHAIN 中的 `[✓]` | 题头显示的推进位置已经经过该步骤 |
| CHAIN 中的 `[⏳]` | 当前等待该步骤的输入事件；后面未标记的步骤尚未推进到 |
| `UNLESS( … )` | 抑制条件；其中任一抑制源为 ON，目标就不能通电 |

CHAIN 的步骤标记表示时序进度，不表示每个上游输入现在仍为 ON。即使步骤都已标为 ✓，活跃抑制仍可使最终结果为 OFF 或 BLOCKED。

## 长期状态与时序进度

permanent 输入跨会话保留，AND/OR 可据此重算长期项目状态。CHAIN 的推进进度属于当前会话，会话重置时清空；适合表达会话内先后发生的事件。长期阶段的完成事实保存在 permanent 输入及正文中。

## 逆向诊断与沙盘推演 (`compile`)

顺着 `read_concept` 题头逐层回溯适合查看单节点的直接前置。当拓扑较深、多层条件交织、或守卫被意外阻断时，使用 `compile` 逆向求解器自动向下递归排查整棵依赖树：

```bash
# 1. 逆向诊断：查看目标为何未就绪/被阻断，直接输出缺失的叶子条件与抑制源
python frontend/cli.py compile --target <目标名或ID>

# 2. 沙盘假设推演：假设若干传感器已被满足，推演下游目标能否导通（不改动任何真实数据）
python frontend/cli.py compile --target <目标名或ID> --assume <传感器A> <传感器B> ...
```

- **目标限制**：`--target` 必须是参与电路的节点（`sensor` / `logic` / `guard`），不能对 `plain` 概念使用。
- **假设限制**：`--assume` 只接受 `sensor` 角色；`logic` 与 `guard` 的电位必须由上游规则推导派生，不可直接 assume。
- **输出诊断**：
  - `[✓ 导通放行]`：条件全部满足，处于就绪状态；
  - `[⛔ 抑制锁死]`：前置已满足，但被活跃抑制源（Inhibitor）切断；
  - `[⏳ 序列等待]`：CHAIN 时序进行中的当前等待步骤；
  - `[✗ 缺少前置]`：列出还需要做到的具体叶子条件（AND 逐项列出，OR 会合并为 "A 或 B"，中间层被抑制则提示 "解除…的抑制"），并在下方附带逐层缩进的完整依赖诊断树。

# 4. 让事件唤起相关记忆

sensor 还可以由事件驱动。`sensor_hook` 匹配用户输入、模型输出、工具调用或工具结果，将传感器置为 1；从 0 到 1 的跃迁会触发 `on_fire`。logic 和 guard 也可以在通电时触发动作，CHAIN 还处理终态迁移。

## sensor 的事件监听与生命周期

只有 `sensor` 角色可以配置 `sensor_hook` 监听运行时事件并驱动电位变化（`logic`、`guard` 与 `plain` 不支持挂载 Hook）。可监听的事件类型：

| 事件 (`event_type`) | 匹配的输入内容 |
| :--- | :--- |
| `user_message` | 用户消息 |
| `model_message` | 已生成的模型回复 |
| `tool_call` | 工具调用，可限定工具名 |
| `tool_result` | 工具结果，可限定工具名 |

绑定 Hook 的 sensor 其 `lifespan` 必须使用 `turn` 或 `session`。`turn` 在回合结束时清零（指模型完成当前轮次的所有工具调用并停机交还话语权时；单轮内的多次连续工具调用仍属同一回合），适合拦截或响应瞬态事件；`session` 保留本会话已发生的事实，换会话重置时清零。两者由 Hook 自动更新；`permanent` 必须手动更新，禁止绑定 Hook。

局部例子：需要在工具输出出现 `TimeoutError` 时得到通知，可以配置：

```bash
python frontend/cli.py create_concept "工具输出中出现TimeoutError" --role sensor --lifespan turn --content "工具返回的文本中匹配到TimeoutError字样时通电。"
python frontend/cli.py set "工具输出中出现TimeoutError" sensor_hook tool_result --match-pattern "TimeoutError"
python frontend/cli.py set "工具输出中出现TimeoutError" on_fire '{"notify": "工具输出包含TimeoutError，请读取错误上下文判断原因。"}'
```

`--tool` 仅在 `tool_call` 与 `tool_result` 下有效，按实际工具名精确匹配（消息类事件严禁指定 `--tool`）；`--match-pattern` 为必填正则表达式，底层按 `re.search(..., re.IGNORECASE)` 执行匹配（全文任意位置命中即可，已默认忽略大小写）。`tool_call` 匹配序列化后的参数 JSON，`tool_result` 匹配工具结果文本。若想匹配指定工具的全部调用而不限制参数或结果，传入 `--match-pattern ".*"`。

`model_message` 在模型输出生成后才匹配，通知在后续回合注入；若希望对用户输入中的线索作出响应，使用 `user_message`。事件选择决定触发时机。

## on_fire 动作

| 动作 | 效果 | 当前状态 |
| :--- | :--- | :--- |
| `notify` | 显示通知文字 | 已接通 |
| `set_focus` | 在 YOU MAY ALSO WANT TO READ 框中推荐读取绑定节点 | 配置可保存，推荐呈现尚未接通 |
| `add_todo` | 待办动作 | 配置可保存，待办效果尚未接通 |

`on_fire` 必须使用标准 JSON 动作对象或列表。需要配置阅读推荐时，引用实际存在且与事件相关的节点：

```text
set <事件节点名> on_fire '{"set_focus":"<待读节点名>"}'
```

设置 on_fire 会替换原动作。单独设置 set_focus 目前不会产生推荐或通知；动作列表可同时保存多项配置，例如 `[{"notify":"通知内容"},{"set_focus":"待读节点名"}]`，其中目前生效的是 notify。

# 5. 用守卫控制匹配的工具调用

guard 将前置条件绑定到工具规则。匹配调用只有在守卫通电（PASS）时才放行；同一调用若匹配多个守卫，需要全部放行。未放行时，Hook Gateway 在 `PreToolUse` 阶段阻止执行。

## 前置条件与工具匹配

在实际需要限制某类调用、且相关条件节点已经存在时，创建守卫并绑定规则：

```text
create_concept <守卫名> --role guard --activation-rule "<前置状态名>" --content "这个前置条件为何决定该调用能否执行，以及适用的调用范围"
set <守卫名> tool_guard <实际工具名> --args-pattern "参数匹配正则"
```

工具名精确匹配；`--args-pattern` 传入正则表达式，底层按 `re.search(..., re.IGNORECASE)` 匹配序列化后的参数 JSON（省略时匹配该工具全部调用）。前置状态为 0 时，匹配调用被阻止；前置成立且没有活跃抑制时放行。多个前置可按实际关系组合，守卫电位不能手动设置。

配置后用 `read_concept` 查看守卫的 Tool Guard 和 Circuit，核对匹配范围及当前放行条件。

## 抑制条件

当某个状态成立应当否决放行时，将已有 sensor 或 logic 作为抑制源：

```text
add <抑制源名> inhibition <目标名>
```

局部行为：前置=1、抑制源=0 时可放行；抑制源变成 1 后，即使前置仍为 1 也会阻止调用。抑制源恢复为 0 后，目标按前置重新求值，原有 CHAIN 进度保留。

抑制源只能是 sensor 或 logic，目标只能是 logic 或 guard，不能自抑制。抑制线可以解除：

```text
delete <抑制源名> inhibition <目标名>
```

修改工具参数与抑制源归零是不同的状态变化；应按传感器的 Hook 和生命周期确认它何时恢复，不能仅因参数已经修改就认定守卫已放行。

## 面对守卫拦截时的处理

工具调用被拦截并非系统崩溃，而是命中图谱门禁。返回消息中已明确指出管辖该调用的守卫名称、缺失的前置条件或锁死它的活跃抑制源。

守卫电位由上游依赖推导求值，不可手动设置。被拦截时，依据实际情境选择处理方式：

- **补齐前置**：若缺失条件是当前任务合理的必要步骤，先执行前置操作让状态通电；
- **调整参数**：若调用参数误触抑制源或存在违规内容，修正工具入参；
- **重构规则**：若守卫规则已过时、产生误伤或不再适用当前目标，直接修正规则或解除守卫绑定；
- **说明缺口**：若需要人类授权或外部关键决策，明确向用户指出阻断原因与具体缺口。

处理拦截就事论事，无需输出道歉、保证或检讨；严禁为了放行而伪造虚假状态。

# 6. 角色约束与图谱维护

## 电路约束速查

| 项目 | plain | sensor | logic | guard |
| :--- | :--- | :--- | :--- | :--- |
| activation-rule | 无 | 无 | 必填 | 必填 |
| lifespan | 无 | 必填 | 无 | 无 |
| 正向上游输入 | 无 | 无 | 必须有 | 必须有 |
| 作为下游输入 | 不可 | 可以 | 可以 | 不可 |
| 作为抑制源 | 不可 | 可以 | 可以 | 不可 |
| 作为抑制目标 | 不可 | 不可 | 可以 | 可以 |
| sensor_hook | 不可 | turn/session，每节点一条 | 不可 | 不可 |
| 手动 set active | 不可 | 仅 permanent | 不可 | 不可 |
| tool_guard | 不可 | 不可 | 不可 | 每节点一条 |
| on_fire | 不可 | 可以 | 可以 | 可以 |

逻辑和守卫电位由依赖派生，不能手动设定。名称、内容和电路必须表达同一个状态；完成信号以实际结果为依据。

## Tag、插件与出口

同类节点增多时，Tag 提供归集入口。可用于判断治理需要的三个信号是：出现第三个同类节点、同型错误再次出现、第二次手工检查同一种违规。它们分别提示分类、写时检查和批量审计的需要。

Tag 插件的 `on_mutation` 可以检查变更并拒绝不合要求的写入，`audit_cluster` 可以检查整个分类。明确的新领域结构也可由插件预先表达。插件开发方法见 [horon-plugin](../horon-plugin/SKILL.md)。

有明确收束目标的分类可以使用系统 Tag `exit`。每个分类最多一个出口，命名为 `{Tag名}-exit`，同时挂分类 Tag 和 exit Tag。出口继承分类名称的语义全宽，正文写明收束目标、完成信号和失败信号。更换出口时，先摘旧节点的 exit Tag，再给新节点挂上。知识分类可以仅用于组织知识。

## 模型与现实的校正

观察记录可以改变事实判断，也可以改变目标和依赖。更新当前值用 patch，保留尝试过程用 append。长期项目的正文应能找回结果依据和路线选择的理由。

图只包含已建模的路径。新证据、他人的成熟经验和图外路线都可以改变计划；未通电可能是工作尚未完成，也可能是前提有误。目标是否值得继续、所谓瓶颈是否成立、是否只在做容易打勾的局部工作，都属于规划本身。

Nocturne Memory 迁移期间，Horon 搜不到相关知识时，仍需查 MCP；Horon 的空结果不能证明记忆不存在。为补齐这处空缺而在 MCP 找到的相关内容，通过 CLI 导出并合并到对应概念；已有内容用补充或修正合并，避免重复副本。

# 7. 命令参考

以下命令均接在 `python frontend/cli.py` 后。

## 节点与检索

| 功能 | 命令 |
| :--- | :--- |
| 创建概念 | `create_concept <名称> --content "正文" [--disclosure "在什么情况下需要打开它"] [--role plain\|sensor\|logic\|guard] [--lifespan turn\|session\|permanent] [--activation-rule "..."] [--on-fire '...']` |
| 读取节点与电路 | `read_concept <名称或ID>` |
| 列出全部节点 | `list_concepts [--tag "Tag 表达式"]` |
| 关键词搜索 | `search_concepts <关键词> [--tag "Tag 表达式"] [--limit 50]` |
| 语义搜索 | `intent "<自然语言查询>" [--limit 10]` |
| 最近修改溯源 | `recent [N]` |
| 逆向求解与诊断 | `compile --target <目标名称或ID> [--assume <传感器1> <传感器2> ...]` |

- `list_concepts` 默认输出全库节点清单；加 `--tag` 作为过滤器按标签筛选。
- `search_concepts` 是文本关键词匹配，`intent` 是基于书腰（disclosure）嵌入向量的语义搜索，`recent` 输出近期被变更的节点摘要。
- `compile` 递归诊断电路节点（sensor/logic/guard）未就绪的前置与活跃抑制，`--assume` 用于沙盘假设推演（不写库）。
- Tag 表达式支持 AND（`TagA & TagB`）与 OR（`TagA | TagB`）。

## 修改节点

| 操作 | 命令 |
| :--- | :--- |
| 修改主名称（重命名） | `set <名称或ID> name <新名称>` |
| 设置书腰 | `set <名称或ID> disclosure "在什么情况下需要打开它"` |
| 转换角色 | `set <名称或ID> role plain\|sensor\|logic\|guard [--lifespan turn\|session\|permanent] [--activation-rule "..."]` |
| 修改激活规则 | `set <名称或ID> activation-rule "规则"` |
| 修改生命周期 | `set <名称或ID> lifespan turn\|session\|permanent` |
| 手动拨动电位 | `set <名称或ID> active <0或1>` |
| 绑定事件感知 | `set <名称或ID> sensor_hook user_message\|model_message\|tool_call\|tool_result --match-pattern "正则" [--tool <工具名>]` |
| 绑定工具守卫 | `set <名称或ID> tool_guard <工具名> [--args-pattern "正则"]` |
| 配置发火动作 | `set <名称或ID> on_fire '<动作JSON>'` |
| 添加/删除别名 | `add <名称或ID> name <别名>` / `delete <名称或ID> name <别名>` |
| 挂载/摘除 Tag | `add <名称或ID> tag <Tag名>` / `delete <名称或ID> tag <Tag名>` |
| 添加/解除抑制 | `add <源名称或ID> inhibition <目标名称或ID>` / `delete <源名称或ID> inhibition <目标名称或ID>` |
| 清除书腰 | `delete <名称或ID> disclosure` |
| 清除规则并退回 plain | `delete <名称或ID> activation-rule` |
| 解绑感知或守卫 | `delete <名称或ID> sensor_hook` / `delete <名称或ID> tool_guard` |
| 删除节点 | `delete <名称或ID>`，删除条件和关联清理见下文 |

- `set role` 用于节点转职（转为 sensor 需附带 `--lifespan`，转为 logic/guard 需附带 `--activation-rule` 以满足底层约束）；若仅调整现有节点的规则或生命周期，直接使用独立的 `set activation-rule` 或 `set lifespan`。
- `set active` 仅允许对 `permanent` 传感器使用；`session` / `turn` 传感器由 Hook 自动感知，禁止手动拨动。
- `sensor_hook` 的 `--tool` 仅在 `tool_call` 与 `tool_result` 时可用，消息类事件严禁指定 `--tool`；`--match-pattern` 为必填。

删除节点时，系统先检查它是否仍被其他节点的 activation-rule 作为成员引用，以及它作为 Tag 源时是否还有其他节点使用该 Tag。有任一情况就拒绝删除，并列出相关节点；需要先修改这些引用或摘除相应 Tag。系统保留概念不可删除，Tag 插件也可能拒绝删除。

允许删除后，节点自身的别名、提醒、Hook、守卫绑定、抑制关系及 Tag 关联等会自动清理；删除组合节点只解除它与输入成员的关联，不删除那些成员。删除未被其他成员使用的普通 Tag 源时，同名 Tag 及其插件文件也会被移除。

正文更新：

```text
update <名称或ID> content --append "新增内容"
update <名称或ID> content --append-file <文件>
update <名称或ID> content --old "旧内容" --new "新内容"
update <名称或ID> content --old-file <旧内容文件> --new-file <新内容文件>
```

## Tag 与审计

```text
create_tag <源概念名>
list_tags
delete_tag <Tag名>
audit <Tag名>
audit --db
audit --all
```

`list_tags` 显示成员数与插件说明。删除 Tag 前需摘除源节点以外成员的该 Tag；系统保留 Tag 不可删除。`audit <Tag名>` 检查该分类，`--db` 检查数据库完整性，`--all` 执行全部 Tag 审计与完整性检查。

## 条件提醒与收件箱

`remind` 保存条件，`inbox` 扫描当前已满足的提醒。它适合查询节点状态、存在性或日期条件，与事件驱动的 on_fire 分开使用。条件持续成立时，再次调用 inbox 仍会返回该提醒；不再需要时按 ID 删除。

```text
remind <关联节点名或ID> --when "条件表达式" --msg "提醒文字"
remind --list [--limit 50] [--offset 0]
remind --del <提醒ID>
inbox
```

条件可使用 `status('名称或ID')`（返回字符串 `'active'` 或 `'inactive'`，不存在为 None）、`exists('名称或组合规则')`、`tags('名称或ID')`（集合）、`TODAY` 和 `NOW`（日期与时间字符串），以及 `and`、`or`、`not` 与比较运算。状态判断使用字符串等值匹配：

```bash
python frontend/cli.py remind "<关联节点名或ID>" --when "status('<条件节点名>') == 'active'" --msg "条件满足时需要收到的提醒"
```

## 批处理、迁移与复位

```text
batch --file <命令文件> [--all]
read_memory <uri> [--out <文件>]
reset
```

- **`batch` 批处理**：文件内每行一条命令（省略 `python frontend/cli.py` 前缀），默认仅输出最后一条命令的结果，加 `--all` 输出全部结果。引号内部支持多行换行文本与 JSON 动作。`batch` 逐行独立提交，中途出错退出时，先前成功的命令**不会自动回滚**；重新运行时**需手动删除或注释已执行成功的行**，否则从头重跑会导致同名创建报错或重复追加正文。
- **`read_memory` 记忆迁移**：从旧版 Nocturne Memory 数据库按 URI 读取正文，加 `--out <文件>` 可直接导出到本地文件，供后续使用 `update --append-file` 合并迁入 Horon 概念。
- **`reset` 临时状态复位**：仅用于脱离 IDE 的**离线终端调试**，手动清空测试残留的临时电位（turn/session 传感器及 CHAIN 进度），保留 permanent 客观事实。在 IDE 正常对话时，系统会在检测到新会话时由 Hook 自动完成重置，无需手动执行。
