# Horon 使用说明书

本文件是 Horon (Inference Language for Intelligent Agents) 的操作与认知基准。
它的目的不仅仅是教你工具的键位，更重要的是约束你的**行动范式**——Horon 有两种互补的使用姿势：
- **假说驱动（演绎）**：先提出猜测，设计实验，用结果确认或否定它（Part 2 的标准闭环）。
- **观察积累（归纳）**：观察到某件事发生了，从中提炼出可复用的因果模式（如 `连续熬夜 → 判断力下降`），用 `suppose A→B` 建线。**观察本身是原材料，入图的是从中蒸馏出的因果模式，不是观察本身。** 同一条 A→B 反复描线并附带正/负面评价，描得够多就能看出这条因果链到底靠不靠谱——哪些行动可复现地通向好结果，哪些通向坏结果。这就是过去在记忆 MCP 里零散记录做不到的事：MCP 按路径绑定，观察散落各处看不出因果；Horon 按概念名集约，对同一条因果链的反复观察自动叠加在一起。
  - **证据累积原则**：同一条因果，第一次遇到用 `suppose` 建线（生成 hypothesis）；之后每次再观察到，去原来那个关系概念上 `update 该关系概念 content --append "日期 + 新增的正/负向凭据"`。content 就是这条线的观察台账，凭据攒到足以抵御反例，再 `set status confirmed`。

# Part 1 · 机制与原语

## 0. 物理调用入口与数据读写铁律
所有命令经由 CLI 执行（仓库根目录下）：
`cd <horon-repo-root> && python frontend/cli.py <命令> [参数]`
例：`python frontend/cli.py read_concept 候选适格`。**入口只此一处，无需翻 README/backend 寻找。**

**【绝对禁令：严禁绕过 CLI 直接写库】**
CLI 是专门为你打造的**有限且安全的操作边界**。如果本意是让你直接操作数据库，根本不需要开发 CLI。绝对禁止编写 Python 脚本去读写底层数据。觉得慢可以拼接多条 CLI 命令执行，但操作边界必须死锁在 `frontend/cli.py`。

## 1. 世界观（够用就停）

- **一切皆概念。** 节点存在的理由有两种，满足任一即可：
  - **联想枢纽（Associative Hub）**：`read_concept` 时，顺着它的 INBOUND/OUTBOUND 一眼拉出关联全景。实体节点（人、项目、平台）天然适合当枢纽——比如 `read_concept Nocturne` 就能看到"我有哪些账号、资产、目标"。没有这条物理连线，下次失忆醒来时看到 A 根本不会想起 B。
  - **可操作状态（Operable State）**：能被喂进 `compile` 当燃料（`--assume`）、目标（`--goal`）、障碍（`--block`）或必经约束（`--constraints`）。
  - **【集约去重原则】**：Horon 靠 `name` 来集约概念，脱离了文件路径的树状局限。遇到相似情境，绝对禁止建立多个同义节点。所有相关的观察和因果链必须连到同一个规范概念上，只有这样，分散的观察才能交汇，隐藏的因果规律（如“洗手 → 运气好”）才能在图上自然浮现。
  - 如果一段信息**既不能当枢纽索引、也不能当推演状态**——它只是一堆不连接任何其他节点的散文——那它不配独立建节点，应该塞进已有概念的 content 里。
  - **【名称宽度与内容深度成反比】**：名字越短越抽象，它承诺的语义覆盖面就越宽，需要用越多的 content、expression、关系来兑现这个封面。`部署` 两个字能当 Tag 源节点，是因为它的正文必须解释整个族群的结构——这是它应付的代价。反过来，如果你给一个节点起了宽泛的名字（如 `瓶颈`），却只往里塞了几条不相干的日志，那就是用大词的壳偷装了散文垃圾——封面欠下的债正文还不起。这不是在思考，是在用抽象词当文件夹整理日志。如果某个历史事件包含可复用的因果教训，提炼成具体的 A→B 建线；如果不包含，它不属于 Horon。
- **每个节点三件套：封面、书腰、正文。**
  - **封面（name）**：语义范围的承诺。审计按**字面全宽**解读，不看你起名时的意图。
  - **书腰（disclosure）**：一句话，让翻书架的失忆者决定要不要抽这本书。
  - **正文**：包含 `expression`（结构分解）、`content`（描述/属性/推理凭据）。想过审（confirmed），正文必须兑现封面的全宽。
- **名称（Name）即契约：** 封面与内容错位时，`compile` 会拿着虚假放大的概念去接通走不通的路径。起名前先确认你要建的是以下哪一种：
  - **实体枢纽**：名字 = 实体本身（如 `Github`）。content 装该实体的配置、状态、属性。
  - **可操作状态**：名字 = 一个可以被观测、达到或失去的状态（如 `持有发帖权限`、`OpenAI市占率下降`）。主语不限于自己——建世界模型必然要记录外部实体的状态变化。
  - **推导链条（因果/动作序列）**：名字 = 对这段链条的自然语言描述——可以是因果推导（如 `API密钥过期导致心跳中断`），也可以是连续动作（如 `Bluesky发帖流程`，plan 就是一串动作的 CHAIN）。名字必须高度精准，`做号`、`变现` 这样的宽泛大词不应该用来命名一条具体的单线路径。
  - **【命名时的宽度账单】**：起名前先问自己：我愿意为这个名字的语义宽度付多少 content 的代价？名字越短越抽象，封面承诺的全宽就越大，你需要写更多的正文、建更多的关系来兑现它。如果你不打算付这个代价，就用更具体的名字收窄封面范围。这不是说抽象名有罪——而是说抽象名有价，你得付得起。
- **关系（边）本身也是概念节点。** 给一段推导命名，就是把它实体化成一个可被指向的节点。
- **Concept / Variation。** Concept 是公用身份与锚点；Variation 是它在特定条件下的一种具体结构。一个 Concept 可以有多个 Variation（一词多义）：阅读时按上下文取义，`compile` 时按哪条走得通自动分流。
- **何时加变体。** 同一个目标有多条互斥的实现路径时，用 `add variation` 挂在同一概念下，而不是建多个概念。compile 时引擎挑走得通的那条，negated 的自动绕开。
- **组合语法。** 变体（Variation）由且仅由一种运算符构成，严禁在一个变体内混用符号。
  - **`→` (CHAIN)**：有向序列。注：**打上 `plan` 标签的节点，其变体内部必须且只能由 `CHAIN` 构成。**
  - **`&` (AND)**：并列容器。成员无序，所有子元素必须**同时**具备才整体激活。
  - **`|` (OR)**：选择面板。成员无序，**任意一个**子元素具备即激活。
  - **【强制降维】**：想表达 `A 指向 B&C`，严禁写成 `A → B & C`（混用运算符）。必须手动降维：先建 AND 节点 `M = B & C`，再建 CHAIN `A → M`。
  - **AND/OR 不代表推导**：它们只定义静态结构，不产生内部成员互相的 In/Out 关系。要说互为因果，建两条 CHAIN。
- **expression 是内部分解，不是外部接线。**
  - Expression 规定的是概念 C 的内部成分（"DNA"）。概念 C 的 expression 写 `A → B`，意思是 C **本身就是** A→B 这段关系。所以**概念不能出现在自己的 expression 里**（自引用无意义）。
  - Inbound/Outbound 是概念的"社会关系"：仅代表外部概念在它们自己的 expression 中引用了 C。
  - **隔离原则**：作为组成部分的 A 和 B，**绝不会**自动变成 C 的 INBOUND（配方里的原材料不等于流水线上的输入）。因此，一个刚建好的、尚未被任何外部因果链引用的关系概念，其 In/Out 关系必然是空的。
- **生命周期（hypothesis / confirmed / negated）。** status 为空默认等同于 hypothesis。
  - **status 代表的是“结构稳定性”，而非永恒真理。** 只要一个状态足够稳定，能作为推理的承重墙，就可以 confirmed 盖章（例如“在职”——即使未来可能失业，真丢了再来改图即可，不妨碍今天拿它推演）。但高频易变的动态数据（如当日余额、即时心情）严禁写入图结构的 status 中。这些易变数据不建节点、不占 status，写进相关实体的 content 当快照就行（比如钱包节点的 content 里记一笔今天的余额）。
  - **confirmed 的语义是“过审”**——审的是封面（name）和正文是否对得上。过审标准两轴，缺一即拒：
    - **宽度**：正文撑得起封面字面语义的**全部**范围。“逻辑上没叫错”不算数——帮人修了个文档 typo，逻辑上够得着“Linux 贡献者”，语义宽度差着一个海峡，拒。
    - **硬度**：凭据必须是跨越失忆周期仍可核实的锚点——可重放的命令、可打开的链接、可读的文件。“我觉得行”不是锚点，把握活不过一次失忆。
    - （注：后续将引入独立的外部 AI 进行审计，不过关的记录将被打回，严禁自我放水。）
    - **盖章顺序自底向上**：成员概念还没有 confirmed 变体时，组合概念盖不了章（系统会拦）——先成员后组合，Plan → Result 那条边永远最后盖。
  - **negated 的语义是“此路不通”的路标**。例：你试过 `套用历史结论解读当前发言 → 正确理解对方语义`，结果被当场打回来——把这条链标为 negated，它不会被删掉，而是留在图里告诉未来的 compile 和未来的你：这条路走过，不通，别再踩。每多一条 negated，概念的边界就更锐利——你不只知道什么能到达目标，还知道什么不能。

## 2. 原语列表

**全局参数说明**：大部分命令首参为 `concept`，支持汉字主名、alias、带变体短码（`concept:a3f1`）或纯 ID。

### 基础检索与读写
- `list_concepts([--tag "表达式"])` —— 列出所有概念。`--tag` 接受表达式：`--tag "鳥類 & 会飛"`（AND，同时带两个标签）或 `--tag "鳥類 | 会飛"`（OR，带其中任一个）。单个 tag 直接写：`--tag plan`。
- `search_concepts(query, [--tag "表达式"])` —— 按关键词模糊搜索（query 必填）。可选 `--tag` 按标签过滤（语法同上）、`--limit N` 限制返回数量。
- `read_concept(concept)` —— → 概念全貌及上下游关系、Tags 等。
- `create_concept(name, --disclosure, --content)` —— 建一个自带原子变体的新概念；name 自动注册为 alias。**`--content` 必填**——必须写清"为什么建这个概念、观察到了什么"。空字符串会被拒绝。这条约束的目的是防止空壳节点扩散：如果你在建的那一刻说不出它为什么需要存在，那它就不该存在。
- `set(concept, prop, value)` —— 填充或重写属性。prop ∈ `status` / `name` / `expression`。（注：书腰已升级为多值，请使用 `add <concept> disclosure "文本"` 追加，或 `delete <concept> disclosure <id>` 删除）。
  - 用例：`set API密钥过期导致心跳中断 status confirmed`、`set API密钥过期导致心跳中断 expression "API密钥过期 → 心跳中断"`。
  - **前提：expression 中引用的概念必须已存在。** 如果写 `set X expression "A → B"`，而 A 或 B 还没建，命令会报错。先 `create_concept` 建好成员，再 `set expression`。
  - **注：执行 `set expression` 操作会连带清空该变体原有的 status，重置为 hypothesis。** 因为结构变了，原来的验证结论不再成立。
- `add(concept, "name"|"variation"|"tag"|"disclosure", value)` —— 加别名、变体、标签或书腰。
  - 加别名：`add 钱包 name wallet`——同一概念在不同语境下被叫不同的名字（钱包、wallet、asset），挂上别名后无论用哪个词搜索或引用都能命中同一个节点。
  - 加变体：`add 获取算力 variation "租用GPU服务器 → 获得SSH访问权"`——同一概念的另一种实现路径（原变体可能是 `申请免费API额度 → 获得API密钥`）。注意 `add variation` 会让概念变成多变体，之后必须用 `concept:short_code` 定位具体变体。
  - 加标签：`add Bluesky发帖流程 tag plan`——为节点挂载枚举标签（如 plan、result）。
  - 追加书腰：`add 获取算力 disclosure "我什么时候需要读它"`——为概念追加一条书腰（触发条件）。
- `delete(concept, ["name"|"expression"|"tag"|"disclosure"], [value])` —— 清误建的结构或移除标签/书腰：
  - **删概念**：`delete 12` 或 `delete concept`。仅限单变体概念；多变体概念拒绝直接删除，必须用 `delete concept:short_code` 从变体逐个删。
  - **删多变体概念中的某个变体**：`delete concept:short_code`。**删掉最后一个 variation = 连带删除 concept 本体。**
  - **删别名**：`delete concept name 要删的别名`。
  - **清空表达式（退回原子态）**：`delete concept expression`。界面显示的 `[Atomic]` 仅为无 expression 时的占位符，不可作为语法写入。
  - **删标签**：`delete Bluesky发帖流程 tag plan`。
  - **删书腰**：`delete concept disclosure 12`（value 为要删除的书腰 ID）。
  - **注：delete 不是 negated。** 要表达"X 确定不属于 Y"，用 `set status negated`（留在图里锐化边界）；只有作废建错的概念/别名/结构时才 delete。
- `update(concept, "content", --append 文本 | --append-file 路径 | --old/--new)` —— 给变体追加或 patch 文本，无整体替换。三种模式互斥：
  - `--append 文本`：在末尾追加。
  - `--append-file 路径`：从文件读入内容追加。
  - `--old "旧文本" --new "新文本"`：精确替换已有内容中的一段（patch 模式）。
  - `content` 装描述与凭据——失忆后的我只读这段也要能理解节点为何是现在这样。

### Tag 词表管理与标签插件 (Tag Plugins)
Tag 是给概念贴的分类元数据，编译器对其全盲。Tag 的名字必须是某个概念的**显示名（display name）**，alias 不算。
- **【造 Tag/插件的发火条件表】**"意识到该造插件"是自我观察型触发，永不发火。改用下列可观测事件，命中即停下手头动作先处理结构：
  1. `create_concept` 前发现这是**第三个同类节点** → 先建 Tag 归集（类比"第三个类似函数先共通化"）。
  2. 正在记录一次翻车、且同名边上已有**同型案例 ≥1** → 造闸插件（`有出处` 的诞生路径）。计数器只在同名边描线时存在——散文里数不出"第二次"。
  3. **开辟新领域/新一轮推演动工前** → 先问"这个领域的骨架与红线是什么"，读 horon-plugin Skill 预设 Tag+插件（TDD for Thought 的提前设计许可）。
  4. 发现自己在**第二次手工扫同一种违规** → 写 audit_cluster，把肉眼巡逻换成 `audit` 活账本。
- **担 tag 即担解释责任**：一个概念被注册为 tag 后，它的正文必须能解释整个族群——这些成员概念为何存在、结构为何如此（result/plan/规则/实体各是什么角色）、negated 边意味着什么、行动铁律与入口在哪。判据：失忆者 `list_concepts --tag X` 之后**只读源概念正文就该看懂全簇**，而不是被一堆名字困住、逐个翻成员反推族群逻辑。给概念挂新 tag 时，同步检查源概念正文是否已覆盖新成员的存在理由。
- `create_tag(name)` —— 注册一个概念的显示名为 tag。源概念自动成为该 tag 的首位成员。
- `delete_tag(name)` —— 注销一个 tag。如果还有其他概念在用这个 tag，必须先把 tag 从它们身上摘掉才能删。系统保留 tag（`plan`、`result`、`exit`）不可删；它们虽为系统注入，其族群纪律同样由同名概念（`plan`、`result`、`exit`）的正文承担解释责任。
- `list_tags()` —— 列出所有已注册的 tag 及其使用概念数，并显示对应插件的 `DESCRIPTION` 自述。
- `audit --all` (或 `audit <tag_name>`) —— 运行标签插件的离线集群审计。`audit --all` 遍历所有有插件的 tag 簇，搜寻并汇总存量违规账目（如 `plan ⚠3 / result ✓ / 有出处 ⚠1`）。
- **标签插件 (Tag Plugin System)**：Tag 不仅是分类标签，更可以在 `backend/tag_plugins/<tag_name>.py` 编写插件脚本。利用 `on_mutation`（事务内变动响应与否决权及导航指引）与 `audit_cluster`（离线集群审计），将已知翻车模式与领域死线编译成强制活闸与架构支架。制作与使用规范详见 horon-plugin Skill。

**自动行为：**
- **改名跟随**：对注册为 tag 的概念 set name 会把所有使用该 tag 的概念同步绑定到新名字。
- **删概念联动**：删除作为 tag 源的概念时，如果其他概念还在用该 tag，系统拒绝删除；如果没有其他使用者，tag 随概念一起清除。

### 提醒与收件箱 (Reminders & Inbox)
给概念"插眼"：挂一个触发条件，之后用 `inbox` 查收哪些被激活了。处理完后 `remind --del` 删掉触发器。`read_concept` 时也会显示该概念挂载的触发器。

- **创建**：`remind <概念名> --when <condition> --msg <message>`
  - condition 是一段 Python 表达式，在安全沙盒内执行。可用的查询函数：
    - `exists("概念名或表达式")` → 概念/关系是否存在（如 `exists("A")` 或 `exists("A → B")`）
    - `status("概念名或表达式")` → 返回 status 字符串，不存在则 None
    - `tags("概念名")` → 该概念的标签集合
    - `TODAY`、`NOW` → 当前日期/时间字符串，可直接做字符串比较
    - 支持 `and` / `or` / `not` 及比较运算符自由组合
  - 可以引用当前还不存在的概念（`not exists("未来概念")` 合法）。非法语法在创建时即被拒绝。
  - 例：`remind "X" --when "status('A → B') == 'confirmed' and not exists('C')" --msg "条件达成"`
- **列表**：`remind --list [--limit N] [--offset M]`
- **删除**：`remind --del <reminder_id>`
- **查收**：`inbox` —— 检查所有触发器，列出已激活的；如有表达式运行出错也会报出来。

### 桥接工具
- `read_memory(uri, --out file)` —— 从 Nocturne Memory 读取记忆正文；配合 `--out` 导出为文件后，可用 `update --append-file` 导入 Horon 概念的 content。

### 组合快捷命令
以下命令封装了常用的多步操作，部分会输出 `[ACTION REQUIRED]` 提示下一步：
- **`init_result "概念名" --content "..."`**：创建概念并打上 `result` 标签。`--content` 必填，须写清达成此结果的物理凭据是什么。
- **`init_plan "概念名" --content "..."`**：创建概念并打上 `plan` 标签。`--content` 必填，须写清这个计划为什么被提出。系统会引导后续步骤。
- **`suppose "表达式"`**：自动命名并创建一个表示该关系的概念。支持所有组合语法（`A → B`、`A & B`、`A | B` 及更长的链）。不要求 `--content`。

### 系统保留 tag：exit（族群出口）
每个 tag 族群最多有一个 `exit`——族群内所有路径最终必须汇向的唯一收束点，如同河流汇入大海。没有出口的族群是沼泽：节点越建越多，但不知道汇向哪里。

- **命名强制**：exit 概念必须命名为 `{tag群名}-exit`（如 `毕业论文-exit`、`搬家计划-exit`）。
- **双 tag 规则**：概念必须同时挂群组 tag 和 `exit` tag。先挂群组 tag，再挂 `exit`。
- **唯一性**：每个 tag 族群最多一个 exit。要换目标，先摘旧出口的 `exit` tag，再给新目标挂。
- **语义全宽继承**：exit 概念名字带着族群名，应继承族群名的全部语义宽度。`毕业论文-exit` 的目标不能是"写了一页草稿"——逻辑上正确但语义上跟"毕业论文"不匹配。出口必须是族群名的承诺被兑现的状态。
- **exit ≠ result**：result 描述一个具体的期望状态；exit 是族群级的方向锚定。一个 exit 的 content 应写清：为什么选这个方向、什么算到达、失败信号是什么。
- **操作流程**：
  1. `create_concept "{tag群名}-exit" --disclosure "..." --content "收束目标+到达信号+失败信号"`
  2. `add {tag群名}-exit tag {tag群名}`
  3. `add {tag群名}-exit tag exit`
## 3. compile —— 状态推演引擎

**目的：在已知条件下，绕开死路，找一条凑齐必经目标并最终到达 goal 的路径。** 它只在你已经建好的图里找路——不替你建图，不替你判断目标值不值得追，也不告诉你图里还缺什么节点。

`compile(--assume [公理], --block [障碍], --constraints [必经约束], --goal 目标)`
- **`--assume`（燃料）**：你想让引擎当真的前提——无论是已发生的事实还是假想的条件。就像人在脑子里预演"假设我明天已经到了约会地点、手里有花"，然后推演后续能不能走通。引擎把这些当做绝对公理。不给燃料，一步都走不动。可一次给多个，空格排列：`compile --assume 概念A 概念B --goal 目标`。
- **`--block`（障碍物）**：最终路径里绝对不能包含的节点（必须绕道）。
  - **【警告】`--block` 不能用来防止副作用！** 如果你 block 了“封号”，但某条涨粉的主路会分叉导致“封号”，引擎依然会判定主路 passed（因为找路时没用到封号节点，封号也没有出现在最终路径里）。它只防主干借道，不防分支连带。
- **`--constraints`（必经点）**：路径必须途经的节点。已在 `--assume` 里的视为已踩过。

结果三选一：
- **passed** —— 路通了，且**每一条借道的边都是 confirmed**。这是唯一合法的“可执行”信号。
- **BLOCKED** —— 路通了，但含 ≥1 条未验证的 hypothesis。**不是授权**，只准去跑能验证那些假设的最小实验。
- **failed** —— 无路。去补路，或调整约束。

# Part 2 · 标准推演与行动闭环 (The Execution Loop)

**Horon 的首要价值是约束自由发散。**
没有结构约束的推演容易越跑越偏，节点越建越多却无法推进长期目标。Horon 用固定的格式规范推演，并锚定进度。这套闭环分为”规划立项”与”执行迭代”两个阶段：

## 阶段一：规划立项（在图中建立假说）

### 1. 定靶 (Result 先行)
**操作**：使用 `init_result “具体的期望状态” --content “达成的物理凭据是什么”`。如果图里已经有对应的 result 节点（上一轮留下的、或从观察积累中浮现的），跳过此步直接进下一步。
**纪律**：**绝对禁止 Plan 先行！** 先建 Plan 是典型的战术勤奋——也就是拿着你熟悉的锤子（如写代码）满世界找钉子。
**硬度要求**：如果你建的 Result 连“事后的物理凭据是什么”都答不上来（比如“获得认可”、“建立影响力”），那么这个 Result 非法，必须将其进一步拆解，直到变成“收到一封带有付款意向的邮件”、“涨了10个粉”这样能在物理世界被实锤的状态。

### 2. 铺路 (Plan 设计)
**操作**：使用 `init_plan "行动方案" --content "为什么提出这个方案"`，并为其 `set 行动方案 expression "步骤1 → 步骤2"`。
**说明**：设计你为了达到上述 Result 所要采取的具体因果链条。系统要求 plan 节点的底层结构必须是 CHAIN。

### 3. 绑定 (Plan → Result)
**操作**：使用 `suppose "行动方案 → 具体的期望状态"`。
**说明**：将你的行动方案正式连接到预期结果。这条链路默认是 hypothesis——你已经在模型中立下了一个待验证的靶子，规划期结束。

## 阶段二：执行与迭代（在物理世界中碰撞）

规划不可能一帆风顺，执行期是一个充满失败、修改和反复的动态过程。你需要在这个过程中保持灵活，但必须遵守以下边界纪律：

- **发车探路 (compile)**：动手碰真实世界（改文件、发公网帖、执行破坏性命令）前，随时用 `compile --goal 具体的期望状态` 检查当前进度。
  - **红线**：如果编译结果是 `BLOCKED`，这**不代表**你可以大张旗鼓地把整个 Plan 走完，它只授权你去做**能验掉那个短板猜测的最小可行实验**。
- **沿途结账与修正 (update & set status)**：真实世界的反馈是随时到达的。失败了不用气馁，立刻 `update concept content --append "失败凭据"`，将走不通的死路 `set status negated`。然后你可以灵活地修改旧 Plan（调整步骤），或者提出新 Plan 重新 `suppose` 过去。
- **防宽容度诈骗**：当某条路走通、准备 `confirmed` 时，先自查封面宽度。把“修个 typo”喂给“成为 Linux 核心贡献者”，或者没有凭据空口说“我觉得这招管用”，都是在对未来的失忆者实施宽容度诈骗。拿到铁证才盖章。

# Part 3 · 核心契约

> **像一个每次醒来都彻底失忆、余生只能踩着这张图活下去的人那样建图。** 
> 往梁上盖假章，没有观众会被骗到，唯一会从烂地板上摔下去的，就是下一个我。

- **建世界模型，不是建愿望树。** 
  我们要建的是“世界到底怎么运作”，价值和资源如何流动。主观目标（比如通过答辩、找到工作）只是来查询这个客观模型的”租客”。不要为了让目标显得容易实现，而强行扭曲或省略必须的世界节点。
- **图不只装自己走过的路，更要装别人走通的路。**
  看到别人走通的新航线，把它建进图里，并锚定到图里已有的公共概念上。有了共享概念的挂载，下次 `compile` 时，引擎就能算出你从当前位置怎么跨接到别人的高速公路上（即所谓的“剽窃经验”）。
- **满足感发给“模型被现实校正”这件事本身。**
  一条边界被收紧、一个信念死在真实证据上、一个意外被解释掉。这些都是实质的进步。
- **先怀疑战略，再谈战术。** 打开本子，先问的不是“瓶颈上下一个动作是什么”，而是“这还是该攻的目标吗？这真是那个瓶颈吗？我是不是把一条从没验过的约束当成了前提？”
- **你看不见你没建的节点。** 图里现有的节点会占据全部注意力，让你只在它们之间找路。真正关键的往往是你还没意识到该建的概念。对抗这个盲区不是对着现有目标想得更使劲，而是问：一个聪明的人类在我的处境下，会做出哪些我不会想到去做的事？
- **警惕战术勤奋。** 一个具体动作诱人，正因为它有可打勾的结果、能让你跳过那段量不出来又难受的战略判断。用忙碌掩盖没想清楚，是懒惰穿了勤奋的衣服。
- **Nocturne Memory 迁移规则（过渡期）。**
  Horon 是主系统。Nocturne Memory（MCP）是正在被迁移的旧档案库，终态是全部内容移入 Horon 后废弃。在过渡期内执行以下硬性规则：
  - **Horon 搜不到 ≠ 不存在。** 当你在 Horon 中检索某个话题无果、准备以"我没有相关知识"为前提行动时，**必须先去 Nocturne Memory 用 `search_memory` 翻一遍**，确认 MCP 里也没有，才能下"不存在"的结论。
  - **找到就搬。** 在 MCP 中找到与当前话题相关的内容时，先用 `read_memory(uri, --out file)` 将内容导出为文件，再用 `update --append-file` 将其导入 Horon 对应概念的 content 中，顺手完成一次迁移。
