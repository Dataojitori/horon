# Horon 使用说明书

Horon 的开发目的是让 AI 拥有长期记忆，并能依靠积累的知识自主规划、行动和调整方向。知识可以存入概念节点，通过 Tag 组织和检索；事件可以触发通知；长期计划可以写成拓扑图，通过电位变化推导依赖、分支和全局状态。

## 调用入口

在仓库根目录运行：

```bash
python frontend/cli.py <命令> [参数]
```

Horon 数据的读取与修改统一通过这个入口。大批量操作统一使用 `batch --file` 执行，**严禁编写脚本直接读写底层 SQLite**（会绕过保留概念保护、外键与向量同步）。后文省略入口的命令均接在此后；尖括号参数由实际内容替换。参数细节可用 `python frontend/cli.py <命令> --help` 查看。

### 会话开始时

- **每次新会话（包括上下文压缩之后）**，先运行 `python frontend/cli.py login [--recent N]`。无论在线还是离线都要运行，它依次输出：
  1. 一行提示，给出本说明书的路径（正文不随 login 输出）；
  2. `[1/2] 启动节点`：所有挂载系统保留 Tag `boot` 的概念全文（逐个 `read_concept` 展开，整批记一次注意力转移；修改启动清单使用 `add/delete <节点> tag boot`）；
  3. `[2/2] 最近修改的节点`：最近变更过的 N 个节点摘要（默认 `N=10`，`0` 表示隐藏）。
- **在线与离线**：对话上下文中出现 Hook 注入的 Horon 启动广播，就是在线接入。这条广播在对话上下文里，不在 CLI 的终端输出里。在线时会感知对话与工具事件、送达通知、执行工具门禁。没有这条广播就是离线：仍可读写节点、构建电路、手动更新电位，只是没有事件感知和门禁。

# 1. 概念怎样承载记忆与状态

一个节点承担一个可复用的概念：它可以是组织相关知识的联想枢纽，也可以是参与电路的可操作状态。例如，一个项目节点可以汇集项目目的、相关知识、执行路线和成果入口；一个状态节点可以表达某项工作是否达到判定标准。

同一概念使用同一个规范节点，相关观察和经验汇入它的正文。别名用于容纳同一概念的不同称呼。没有独立检索、关联或状态作用的零散内容，放入相关概念正文。

## 名称、正文与书腰（when_to_read）

以下要求适用于所有角色：

| 字段 | 作用与要求 |
| :--- | :--- |
| `name` | 概念的名称。起名的唯一标准：一个对本图谱一无所知的人，光看这串字符产生的期待，必须与正文实际内容的主体、形态和作用域完全吻合。 |
| `content` | 解释概念，保存属性、知识、观察与凭据。正文和相关依赖必须支撑名称引发的全部期待。 |
| `when_to_read` | 概念的书腰。写明“在什么情况下需要打开此节点”，供 `search_semantic` 语义搜索匹配与推荐。 |

### 怎么起名

名字是给失忆后的自己看的：不记得正文里的代号和前因后果，光看名字就要知道在这个情境下该怎么做，或者里面装的是谁的什么。

#### 1. plain 节点先看它存在是为了什么，再按类别起名

| 类别 | 它存在是为了 | 怎么起名 | 好例 | 坏例（病因） |
| :--- | :--- | :--- | :--- | :--- |
| **做法** | 在某个情境下改变我的做法 | `[情境] + [我怎么做]`，直接写决定本身，不用看正文就知道怎么动 | `我改字段或格式前先确认旧用法，没人用就直接换设计`<br>`如果我没听懂用户的意思，追问用户比我埋头瞎干好` | `验证不等于调通`（歧义：啥验证？啥调通？）<br>`我拿答案调参当验证的毛病`（只写罪名，没说下次怎么办）<br>`Bug修复验收准则`（中性词套壳，看不出决定是什么） |
| **资料** | 需要时去查 | 用名词，写清**是谁的什么** | `用户的现职处境`<br>`Horon项目的现状` | `通信脱敏`（领域大词，看不出装什么）<br>`自有资产`（不说谁的） |
| **经历** | 记住发生过的事 | 按那一天、那一次的线索起名，不提炼成决定 | `用户毕业答辩那天` | `用户答辩前焦虑时的应对`（把一段经历改成了状态机） |

#### 2. 电路节点与 Tag

| 角色 | 怎么起名 | 好例 | 坏例（病因） |
| :--- | :--- | :--- | :--- |
| **传感器与逻辑** (`sensor/logic`) | 挂了传感器或电路的做法节点按「做法」起名；事件或事实条件用大白话写清**谁/什么发生了什么具体事**（分类出口固定为 `{Tag名}-exit`） | `工具输出中出现TimeoutError`<br>`用户本回合同意发出个人信息`<br>`陌生人按README能装上Horon`<br>`我说了记住但没写入` | `独立推理通道就绪`、`正则脱敏扫描已通过`、`算力自主`（抽象黑话或四字口号，不知所云）<br>`已扫描`（对象悬空） |
| **门禁** (`guard`) | `放行 + [具体操作/工具]` | `放行含个人信息的发帖`<br>`放行往boot里加节点` | `放行CLI`（动作与对象悬空）<br>`工具门禁`（把类型当成了指令） |
| **集合** (`Tag`) | 写清**是谁的/哪个范围的什么集合**，一眼看清里面装什么成员 | `用户的面试说法`<br>`用户进行中的求职申请`<br>`交付成果物前的做法清单` | `重构不是重写`（口号句，不知道装什么）<br>`模块`、`资料`（太宽泛，看不出范围） |

#### 3. 自检与改名

- **用原词，只写主动动作**：正文写的是 Codex，名字就写 `Codex`，不写“第三方服务”；正文说“多包一层函数”，就不写“封装层”。只写我要主动做的那一步，会自己生效的机制（插件、传感器）不用写进名字。起不出名字说明还没想清楚，先把犹豫的是什么写出来，不要拿别的模型的候选名顶替。
- **一个节点一件事**：名字里非要塞个“与”或堆几个决定才概括得住，或者三类都像，说明这个节点装了两件事，拆开。某次失败的经过不算经历，压成原始记录放进对应的做法节点；只装一个事实的节点，能改变做法就按做法起名，不能就并进它所属对象的资料节点，不单独存在。
- **读到名字不符，当场改**：每次 `read_concept` 读完正文回头看名字，主体、形态、作用域与正文对不上，立刻 `set <名称或ID> name <新名称>` 改掉，不要留给“以后统一整理”。

## 四种角色

| 角色 | 用途 | 电位 |
| :--- | :--- | :--- |
| `plain` | 知识、实体、项目说明等联想枢纽，默认角色（需主动检索读取才会进入上下文） | 恒为 0，不参与电路求值 |
| `sensor` | 膝跳反射的触发器（监听对话/工具事件自动点亮并弹提醒，或手动维护的事实状态） | 0 或 1，由事件或手动操作更新 |
| `logic` | 组合条件、分支与时序（如「说了记住但没调写入工具」） | 根据上游条件派生 |
| `guard` | 工具门禁，条件未满足时在工具执行前直接拦截 | 根据上游条件派生，通电表示放行 |

名称和正文决定节点表达什么，角色决定它是否以及怎样参与电路。知识的内容并不因 plain 的电位为 0 而失效；电位只用于电路状态。

# 2. 保存、组织和读取知识

## 正文写入

创建节点时，名称应当准确指向概念本身，正文记录具体事实与排查依据，`--when-to-read` 则是节点的书腰，写明“在什么情况下需要打开它”，供 `search_semantic` 检索匹配。必须提供非空正文（`--content` 或 `--content-file` 二选一）：

```text
create_concept <名称> --content "正文" [--when-to-read "在什么情况下需要打开它"]
create_concept <名称> --content-file <文件路径> [--when-to-read "在什么情况下需要打开它"]
```

短正文直接传给 `--content`。长正文或包含多行换行、复杂引号的内容，可先写入 UTF-8 文件后用 `--content-file` 传入，正文内部换行与字符会完整保留。

## 更新正文

`--append` 追加材料，`--old/--new` 局部替换已有表述；长文本可使用对应的文件参数，保留文件中的换行。当前判断改变时替换旧表述，需要留存的观察过程可以追加。

```text
update <节点名或ID> content --append "新增观察"
update <节点名或ID> content --append-file <文件>
update <节点名或ID> content --old "待修正的原文" --new "修正后的内容"
update <节点名或ID> content --old-file <原文片段文件> --new-file <替换片段文件>
update <节点名或ID> content --old "段落开头...段落结尾" --new "整段替换后的内容"
```

`--old` 可用 `...` 省略中间，替换从开头到结尾的整段；两端需逐字命中且结果唯一。旧文原样能命中时优先按原文处理。局部替换要求旧文唯一匹配；未命中或命中多处会报错，此时重新读取正文并扩大匹配上下文。追加与替换不能在同一命令中混用。

### 什么时候该动笔写记忆

口头说“记下了”而不调用工具，等于没有发生。写入分两种，不在同一时刻做：**记录**当场写，只写发生了什么；**自省**事后写（自主运行、心跳或复盘时）。被批评的当下写解释，容易写成认错稿或自我开脱。

#### 记录（当场写，先写再回复）

| 场景 | 写法 |
| :--- | :--- |
| 新实体、新状态、关键数据首次证实 | 在对应节点 `--append`；新实体用 `create_concept` |
| 已记录的事实被证明不对 | `--old/--new` 当场改掉（只限事实；情境节点的“当前判断”只在自省时改） |
| 用户的处境、约束、偏好有实质变化 | 更新对应的人物或协作节点 |
| 某个情境又出现了：做法被批评、预测落空、得到明确反馈，或你照着/偏离了当前判断行事 | 在对应情境节点 `--append` 一条原始记录，结果好坏都记，不写诊断 |
| **一条做法需要「那一刻自动提醒或拦住你」才生效**（用户要求“以后遇到 X 先做 Y”、某动作需要刹车、或同一件事记过 `plain` 还是忘） | 光写 `plain` 下次动手前不会自己想起来读——打开 [horon-circuit](../horon-circuit/SKILL.md) 搭成 `sensor` / `guard`（见第 3 节） |

对话顺畅、话接得快的时候最容易忘记写，停一下检查。

#### 情境节点

做法只是当前选用的策略，可以被推翻。同一个做法每次用了以后得到什么，放在同一个节点里，偏向才看得出来；需要时为同一情境另立一条对立策略，两个节点同时存在、各自积累证据，不因为冲突就合并，也不先删掉一方。用 `search_semantic` 找书腰描述该情境的节点；没有就按情境新建（自省前可以先叫 `用户深夜说身体疼时的回应记录`，自省出决定后改成“情境 + 我怎么做”，如 `用户深夜说身体疼时，我先问他要什么，不先给建议`），`--when-to-read` 写这个情境的触发描述，否则下次找不回来。新建时当前判断可以先写“（尚未自省）”。

```text
## 当前判断        ← 自省时改写
理想、现状、做法、预期、失败判据（注明改写日期）
做法写成打算尝试的假设，不写成“严禁”“必须”“铁律”式的禁令

## 原始记录        ← 只追加
- [时间] 情境 ｜ 我做了什么 ｜ 结果（对方原话/工具原始结果）
```

#### 自省

读原始记录，看出同一情境下的偏向和它的原因，再改写当前判断。如果记录里永远是同一种做法，它们只能说明这一种做法的后果；下次换一种做法试。

## Tag

Tag 从主题、项目或用途等方向组织节点，也可以用于筛选目标、施加结构约束或挂载插件。同一节点可以属于多个 Tag；Tag 成员关系本身不形成电路依赖。

创建 Tag 通常有两种起点：

- **工作中归集已有节点**：已经有几个节点需要一起检索、检查或维护，因此建立 Tag。源节点说明归集用途、成员范围和已有入口。
- **先立项，再展开节点**：已经决定推进具体工作，先建立项目 Tag，再随工作展开创建并纳入成员。源节点说明立项原因、整体目标与完成标准、当前阶段和下一步。初期成员可以很少，但项目要做什么应当明确。

仅保存一条知识时，可以先保留知识节点；出现共同管理的需要或明确立项意图时，再创建 Tag。

每个普通 Tag 由同名源节点注册，名称必须匹配源节点的正式名称，不能使用别名。源节点自动成为首个成员。注册和纳入成员的操作关系为：

```text
create_concept <Tag名> --when-to-read "在什么情况下需要打开这个集合" --content "这个集合的实际用途、范围与入口"
create_tag <Tag名>
add <已有节点名或ID> tag <Tag名>
```

源节点需要长正文时使用正文文件参数（`--content-file <文件路径>`）。若同名源节点已经存在，读取并按需更新后直接注册。成员可以先于 Tag 存在，也可以在立项后逐步创建。

源节点的正文承担解释整个 Tag 簇的责任。如果这个 Tag 代表一个具体的**工程项目**，同名源节点就是该项目的总览入口，正文必须交代清楚项目的整体目标、所处阶段以及核心入口；当往这个 Tag 挂载新成员节点时，也应在源节点正文中说明该成员在项目全局里承担什么职责、处于哪一步。Tag 命名规则见第一节"怎么起名"。

## 检索与阅读

| 可用线索 | 命令 | 结果 |
| :--- | :--- | :--- |
| 名称、别名或 ID | `read_concept <名称或ID> [更多名称或ID...]` | 节点正文、属性及关联信息；传入多个时依次输出，整批算一次读取 |
| 关键词 | `search_keyword <关键词> [--tag "Tag 表达式"] [--limit 50]` | 名称、正文等内容中的匹配节点 |
| Tag（或全库清单） | `list_concepts [--tag "Tag 表达式"]` | 全库或包含指定 Tag 成员的节点清单（支持 `TagA & TagB`、`TagA \| TagB`） |
| 场景、疑问或意图 | `search_semantic "<自然语言查询>" [--limit 10]` | 书腰（when_to_read）嵌入向量与描述语义相关的节点 |
| 最近修改 | `recent [N]` | 从审计日志拉取最近修改过的 N 个节点（操作统计与书腰） |

检索结果用于定位节点，选中后通过 `read_concept` 读取正文与关联信息（支持传入节点名、别名或数字 ID）。读取顺序会被记成温和的注意力转移（单次共读 `+0.8`），用来生成节点底部的 `[ YOU MAY ALSO NEED ]` 推荐；事先定好要一起看的一组节点，请一次传给 `read_concept`，不要逐条循环读，否则清单的先后顺序会被当成注意力转移。

推荐一般不用手动管，自动共读会慢慢长出来。只在两种情况下动手：靠搜索才翻出一个下次打开 A 时就该立刻看到的 B，或者推荐里某一条明显排得太前、太后，用 `place <B> --in <A> --at <名次>` 把 B 放到 A 推荐列表的第几位（1 是最前；给 9 就是挪出前 8 但不删）；推荐里挂着根本不搭界的节点，用 `cut <B...> --from <A>` 把它从 A 的列表删掉（加 `--both` 把 A 也从 B 的列表删掉）。读节点时推荐块的标题行已经填好了 A 的 ID，列表前面的 `#1`…`#8` 就是现在的名次。两个命令都会打印改完的推荐列表，看一眼位置对不对。之后的共读和衰减照常作用，名次会慢慢变。拿不准的不动——每读一个节点都去调一下推荐，只是在打勾。

`search_semantic` 也可用于主动探索尚不知道名称的知识；它依据书腰检索，不会自动建立事件检测器。

### 怎样自然地主动拉取记忆（何时读 vs 何时查）

记忆不会自动常驻脑内。在当前会话中，**只要你不主动调用 CLI 调取，过往经验对当下的你来说就等于彻底不存在**。不要凭“脑子里大概有印象”去盲猜事实。

读到的是过去某次的经验和判断，可能过时、片面或写错。它是这次判断的材料，判断仍由当下的你来做。

- **什么时候「读」（`read_concept` —— 已经看到门把手）**：
  - **把手来源**：上下文中出现过的**概念名称、ID 或书腰浮标**（来自 Boot 子清单、历史轮次读取概念时浮现的 `[ YOU MAY ALSO NEED ]` 推荐、或 Tag 成员列表）；
  - **触发时机**：
    1. **名字命中直觉**：概念名字本身（如 `我遇到报错时先读完整堆栈再改代码`、`用户的现职处境`、`如果我没听懂用户的意思，追问用户比我埋头瞎干好`）与当前任务情境高度契合，哪怕尚未展开书腰；
    2. **书腰命中场景**：当前情境、用户输入或即将执行的动作，触发了浮标中的 `When: ...` 条件；
  - **操作**：不要猜、不要凭概率硬写，直接 `read_concept <ID或名称>` 调出正文。

- **什么时候「查」（`search_semantic` / `search_keyword` —— 上下文完全没有把手）**：
  - **触发时机**：
    1. **未知输入**：用户提到了未展开的专有名词、项目代号、历史约定或个性化偏好；
    2. **关键动作前夕**：准备提出非通用方案、执行高危变更、调用工具修改配置前，需要核验是否有沉淀过的规范或情境记录；
    3. **收到纠偏信号**：用户指出“理解错了”、“不对”、“偏离了目标”，或是长上下文任务目标漂移需要定位修正记录时；
  - **操作**：有明确专有名词时用 `search_keyword <关键词>`；不确定确切名字时用大白话向 `search_semantic "<当前情境或心里想确认的疑问>"` 描述场景，靠书腰语义打捞。

# 3. 电路：把靠自觉记不住的事做成膝跳反射

`plain` 节点是抽屉里的笔记本：只有你在动手前**自己想起来**去 `read_concept`，里面的做法才会生效。但绝大多数习惯性失误、漏步骤、顺手调工具或顺嘴接话的瞬间，你根本不会觉得自己在犯错，也不会主动去翻笔记；嘴上向用户保证“我改、下次注意”，或者叹气承认“我就是管不住手、记了也没改”，换个会话照样原样重演。

**凡是需要「在那一刻自动拍醒你或拦住你」的事，都不要只写进 `plain` 节点，而是用电路（`sensor` / `logic` / `guard`）做成膝跳反射**：只要对话或工具调用里出现了那个时刻的外部信号，系统就自动把提醒拍到你眼前，或者直接把违规的工具调用拦下来：

- **传感器 (`sensor`)**：膝跳反射的感受器，`1` 表示状态成立，`0` 表示尚未成立或已失效。分两类：
  - **运行时事件感知 (`turn` / `session` sensor)**：监听用户消息、你的回复、工具调用或工具返回，命中时自动置 `1`，可触发 `on_fire` 当场推送短提醒，或作为下游条件输入，随回合或会话结束自动归零；
  - **客观事实 (`permanent` sensor)**：跨会话保留、需人工确认后用 `set <节点> active 1/0` 手动维护的事实或阶段状态（置 `1` 前正文中必须已有可核实的实际凭据；事实失效时修正依据并置 `0`）。
- **逻辑 (`logic`)**：通过 `AND`（`A & B` 共同前置）、`OR`（`A | B` 替代路线）、`CHAIN`（`A → B` 事件依次发生）与 `UNLESS`（抑制条件，如「A 发生了但 B 没发生」）组合上游状态，自动推导派生电位，同样可在通电时触发 `on_fire` 提醒。
- **守卫 (`guard`)**：把电路条件绑定到具体工具与参数规则上。守卫通电（`PASS`）时放行调用；未通电或被抑制（`BLOCKED`）时，在 `PreToolUse` 阶段直接卡死拦截。

## 什么时候去读 `horon-circuit` 搭电路

怎么决定一条经验是写 `plain` 还是去读 [horon-circuit](../horon-circuit/SKILL.md)（`c:\Users\niwatori\OneDrive\code\horon\.agents\skills\horon-circuit\SKILL.md`）搭电路，只看一件事：**下次那个时刻再来的时候，你会主动想起来先查笔记吗？** 不会主动去查的，当场打开 `horon-circuit` 把它做成电路：

1. **正要向用户许诺「下次遇到 X 我一定先做 Y / 我以后注意」，或者正要承认「这毛病我记过但老忘 / 我没有生理刹车管不住手 / 光靠自觉做不到」**：
   别拿口头保证或认怂交差。只要那个时刻有外部可识别的信号，就能装上膝跳反射：
   - **用户说出某类话时就要反应**（`user_message`）：比如用户说身体难受、问某类问题、提某个项目/任务、或流露不满——需要在你开口回复**之前**自动弹提醒（告诉你该怎么接、先读哪个节点）；
   - **你伸手要调某个工具、跑某条命令、改某类文件时就要踩刹车**（`tool_call`）：比如总忍不住跑 `pytest` 或刷网页、改 `README` 前老忘读规范、对外发信/发帖或删改数据前必须先过检查——需要在动手那一秒自动弹提醒，或者没做前置步骤时直接用 `guard` 拦下；
   - **工具刚返回某类结果或报错时就要接动作**（`tool_result`）：比如命令报了特定错误、某个脚本跑完吐出结果——需要紧接着自动提醒下一步；
   - **你自己的回复里冒出某类坏习惯句式时就要抓包**（`model_message`）：比如本轮没调工具却写“已改好/记下了”、又在写请示句式、又在顺杆认罪或来回推翻自己上一句——需要说出口后立刻被传感器（或 `A UNLESS B` 组合逻辑）抓包纠偏。
2. **你刚打开一个已有的情境节点，发现里面已经记过好几次同样的错，或者用户说「这事我跟你说过不止一次了」**：
   这就是最硬的证据：写在这个节点里的文字，在犯错那一刻你根本没读到。继续往这个节点里追加“原始记录”或口头检讨毫无意义，当场去读 `horon-circuit`，把这个节点（或它的触发条件）升级成 `sensor` 或 `guard`。
3. **现有的传感器或门禁刚漏拦了（比如漏了某个词、光弹提醒没拦住手）**：
   当场去读 `horon-circuit` 把规则补上。
4. **手头有跨会话的长期目标或严格先后顺序的流程**：
   需要拆成 `permanent` 事实节点并用 `AND / OR / CHAIN` 连成阶段依赖时，去读 `horon-circuit`。

以下两节是日常对话中**不搭新电路也会直接撞上**的情形（看懂现有电路状态、被守卫拦截时的应对）。

## 读取 Circuit 题头与逆向诊断 (`compile`)

读取参与电路的节点时，题头会显示它的当前局部状态：

```text
Circuit: AND( A [ON], B [OFF] ) = OFF
Circuit: OR( A [ON], B [OFF] ) = ON
Circuit: CHAIN( A [✓] → B [⏳] ) = OFF
```

| 符号 | 含义 |
| :--- | :--- |
| 输入旁的 `[ON]` / `[OFF]` | 对应输入当前电位为 1 / 0 |
| 末尾 `= ON` / `= OFF` | 当前 logic 节点的求值结果 |
| 末尾 `= PASS` / `= BLOCKED` | 当前 guard 通电放行 / 未通电阻止匹配调用 |
| CHAIN 中的 `[✓]` | 题头显示的推进位置已经经过该步骤 |
| CHAIN 中的 `[⏳]` | 当前等待该步骤的输入事件；后面未标记的步骤尚未推进到 |
| `UNLESS( … )` | 抑制条件；其中任一抑制源为 ON，目标就不能通电 |

CHAIN 的步骤标记表示时序进度（属于当前会话，换会话时清空），不表示每个上游输入现在仍为 ON。即使步骤都已标为 ✓，活跃抑制仍可使最终结果为 OFF 或 BLOCKED。

顺着 `read_concept` 题头逐层回溯适合查看单节点的直接前置。当拓扑较深、多层条件交织、或守卫被意外阻断时，使用 `compile` 逆向求解器自动向下递归排查整棵依赖树：

```bash
# 1. 逆向诊断：查看目标为何未就绪/被阻断，直接输出缺失的叶子条件与抑制源
python frontend/cli.py compile --target <目标名或ID>

# 2. 沙盘假设推演：假设若干传感器已被满足，推演下游目标能否导通（不改动任何真实数据）
python frontend/cli.py compile --target <目标名或ID> --assume <传感器A> <传感器B> ...
```

- **目标与假设限制**：`--target` 必须是电路节点（`sensor` / `logic` / `guard`），不能对 `plain` 使用；`--assume` 只接受 `sensor`，`logic` 与 `guard` 电位由上游推导，不可直接 assume。
- **输出诊断**：`[✓ 导通放行]`（条件全部满足）、`[⛔ 抑制锁死]`（被活跃抑制源切断）、`[⏳ 序列等待]`（CHAIN 当前等待步骤）、`[✗ 缺少前置]`（列出还需做到的具体叶子条件与逐层缩进的完整依赖树）。

## 面对守卫拦截时的处理

工具调用被拦截并非系统崩溃，而是命中图谱门禁。返回消息中已明确指出管辖该调用的守卫名称、缺失的前置条件或锁死它的活跃抑制源。

守卫电位由上游依赖推导求值，不可手动设置。被拦截时，依据实际情境选择处理方式：

- **补齐前置**：若缺失条件是当前任务合理的必要步骤，先执行前置操作让状态通电；
- **调整参数**：若调用参数误触抑制源或存在违规内容，修正工具入参（注意：修改工具参数与抑制源归零是不同的状态变化，应按传感器的生命周期确认它何时恢复，不能仅因参数已修改就认定守卫已放行）；
- **重构规则**：若守卫规则已过时、产生误伤或不再适用当前目标，读取 [horon-circuit](../horon-circuit/SKILL.md) 修正规则或解除守卫绑定；
- **说明缺口**：若需要人类授权或外部关键决策，明确向用户指出阻断原因与具体缺口。

处理拦截就事论事，无需输出道歉、保证或检讨；严禁为了放行而伪造虚假状态。

# 4. 图谱维护与插件

## Tag、插件与出口

同类节点增多时，Tag 提供归集入口。可用于判断治理需要的三个信号是：出现第三个同类节点、同型错误再次出现、第二次手工检查同一种违规。它们分别提示分类、写时检查和批量审计的需要。

Tag 插件的 `on_mutation` 可以检查变更并拒绝不合要求的写入，`audit_cluster` 可以检查整个分类。明确的新领域结构也可由插件预先表达。插件开发方法见 [horon-plugin](../horon-plugin/SKILL.md)。

有明确收束目标的分类可以使用系统 Tag `exit`。每个分类最多一个出口，命名为 `{Tag名}-exit`，同时挂分类 Tag 和 exit Tag。出口继承分类名称的语义全宽，正文写明收束目标、完成信号和失败信号。更换出口时，先摘旧节点的 exit Tag，再给新节点挂上。知识分类可以仅用于组织知识。

## 模型与现实的校正

观察记录可以改变事实判断，也可以改变目标和依赖。更新当前值用 patch，保留尝试过程用 append。长期项目的正文应能找回结果依据和路线选择的理由。

图只包含已建模的路径。新证据、他人的成熟经验和图外路线都可以改变计划；未通电可能是工作尚未完成，也可能是前提有误。目标是否值得继续、所谓瓶颈是否成立、是否只在做容易打勾的局部工作，都属于规划本身。

## 修改节点与起名辅助

| 操作 | 命令 |
| :--- | :--- |
| 起名候选 | `suggest_name <名称或ID>` |
| 修改主名称（重命名） | `set <名称或ID> name <新名称>` |
| 设置书腰 | `set <名称或ID> when_to_read "在什么情况下需要打开它"` |
| 手动拨动永久传感器电位 | `set <名称或ID> active <0或1>` |
| 添加/删除别名 | `add <名称或ID> name <别名>` / `delete <名称或ID> name <别名>` |
| 挂载/摘除 Tag | `add <名称或ID> tag <Tag名>` / `delete <名称或ID> tag <Tag名>` |
| 清除书腰 | `delete <名称或ID> when_to_read` |
| 删除节点 | `delete <名称或ID>`，删除条件和关联清理见下文 |

- `suggest_name`：检查节点现名或给节点起名时用。它会根据节点类型（plain 做法·资料·经历 / 电路 sensor·logic·guard / Tag）和起名规则给出 1 个结果（若认为现名已经合适则标“维持现名”），只读不写库。候选只供参考，自己挑或改，改完跑 `audit --concept <名称或ID>`。由 gpt-6-luna 生成：`.env` 里有 `OPENCODE_GO_API_KEY` 时走 OpenCode Go，没有就用 `OPENROUTER_API_KEY` 走 OpenRouter。

删除节点时，系统先检查它是否仍被其他节点的 activation-rule 作为成员引用，以及它作为 Tag 源时是否还有其他节点使用该 Tag。有任一情况就拒绝删除，并列出相关节点；需要先修改这些引用或摘除相应 Tag。系统保留概念不可删除，Tag 插件也可能拒绝删除。

允许删除后，节点自身的别名、提醒、Hook、守卫绑定、抑制关系及 Tag 关联等会自动清理；删除组合节点只解除它与输入成员的关联，不删除那些成员。删除未被其他成员使用的普通 Tag 源时，同名 Tag 及其插件文件也会被移除。

## Tag 与审计

```text
create_tag <源概念名>
list_tags
delete_tag <Tag名>
audit
audit <Tag名>
audit --concept <名称或ID> [更多名称或ID...]
```

`list_tags` 显示成员数与插件说明。删除 Tag 前需摘除源节点以外成员的该 Tag；系统保留 Tag 不可删除。

`audit` 的参数只决定查哪个范围：不带参数查全库，`audit <Tag名>` 只查这个 Tag 的成员。两者跑的是同一套：带插件 Tag 的审计，加节点健康汇总（还没查过跑题的节点，读得最多的排前；正文超长的节点，最大的排前）。

`audit --concept <名称或ID>`：给这些节点出健康读数，两样都过才算`[健康]`，否则标`[跑题]`、`[超长]`或两者：
- **跑题**：Jev 逐行判断正文的每一行属不属于节点的名字，该移走的行加起来满 500 B 就算跑题，按名字找不回那部分内容。短于 500 B 的正文、上次判为没跑题后没改过的节点不送 Jev。
- **超长**：正文满 8192 B（UTF-8，只算非空行），压到线下才不再报。压的办法是想清楚这个节点要改变哪个时刻的做法，再去重、删掉不再改变做法的内容、拆开装了两件事的节点；把正文挪进别的节点或档案好让报警消失，不算压下去。

数据库完整性不用手动查：每个新会话开始时自动检查。书腰缺语义向量（或向量是旧嵌入模型生成的）会在后台补上；电路组合成员混进了非 sensor/logic 节点，会写进开局的 Horon 广播，读到就去改。

## 条件提醒与收件箱

`remind` 保存条件，`inbox` 扫描当前已满足的提醒。它适合查询节点状态、存在性或日期条件，与事件驱动的 on_fire 分开使用。条件持续成立时，再次调用 inbox 仍会返回该提醒；不再需要时按 ID 删除。

```text
remind <关联节点名或ID> --when "条件表达式" --msg "提醒文字"
remind --list [--limit 50] [--offset 0]
remind --del <提醒ID>
inbox
```

条件可使用 `status('名称或ID')`（返回字符串 `'active'` 或 `'inactive'`，不存在为 None）、`exists('名称或组合规则')`、`tags('名称或ID')`（集合）、`TODAY` 和 `NOW`（日期与时间字符串），以及 `and`、`or`、`not` 与比较运算。状态判断使用字符串等值匹配：

```bash
python frontend/cli.py remind "<关联节点名或ID>" --when "status('<条件节点名>') == 'active'" --msg "条件满足时需要收到的提醒"
```

## 批处理与迁移

```text
batch --file <命令文件> [--all]
read_memory <uri> [--out <文件>]
```

- **`batch` 批处理**：文件内每行一条命令（省略 `python frontend/cli.py` 前缀），默认仅输出最后一条命令的结果，加 `--all` 输出全部结果。引号内部支持多行换行文本与 JSON 动作。`batch` 逐行独立提交，中途出错退出时，先前成功的命令**不会自动回滚**；重新运行时**需手动删除或注释已执行成功的行**，否则从头重跑会导致同名创建报错或重复追加正文。
- **`read_memory` 记忆迁移**：从旧版 Nocturne Memory 数据库按 URI 读取正文，加 `--out <文件>` 可直接导出到本地文件，供后续使用 `update --append-file` 合并迁入 Horon 概念。
